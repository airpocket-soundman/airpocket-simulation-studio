## Preflight review of session/new

The same bundle's `newSession` sets skills roots, creates session config, calls `thread/start` and `model/list`, and reads authentication status. It does not directly call `turn/start` or authenticate; title generation follows prompt completion. Metadata creation may nevertheless persist thread management state or start MCP servers.

Default AgentMode is `agent`: auto_review with workspaceWrite and networkAccess=false. `INITIAL_AGENT_MODE=read-only` controls session state and later prompts, but alone does not constrain `thread/start`. `createSessionConfig` marks cwd trusted and returns inherited configuration unchanged when `mcpServers:[]`. An empty MCP table does not establish that inherited servers are disabled. User configuration contained two MCP definitions, twelve plugin definitions and no inline hooks. Names, URLs, identifiers and values were not retained as evidence.

The [official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) documents `sandbox_mode="read-only"`, `features.hooks=false`, per-server `mcp_servers.<id>.enabled=false`, and `plugins.<plugin>.enabled=false`. The existing client does not expose effective-config readback before session creation, however, so disabling every configuration layer and workspace-managed plugin is not established. The adapter separates only hooks from `CODEX_CONFIG` into startup arguments; the remaining configuration is passed at thread creation. Under the required condition that read-only mode, disabled hooks and all-disabled MCP be demonstrated first, session/new was therefore **not executed**. Global settings and authentication were not changed to bypass this condition.
