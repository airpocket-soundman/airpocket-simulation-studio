## 実装・物理・状態の共通条件

- 個別ファイルの「今回の完了条件」は親タスク全体の完了条件ではない。progressの既存IDを使い、似たカードを重複追加しない。
- 物性・荷重・支持・校正値・測定値を発明しない。合成テスト入力は「合成」と明記する。
- 表示倍率を載荷履歴、最大von Mises応力を工学応力、単独成功を一般的精度保証と呼ばない。
- `completePreflight:false` を維持する。preflight成功を物理妥当性・メッシュ品質・収束・精度の合格へ読み替えない。
- GUI/API/MCPで意味、単位、入力版、取消、保存互換性を一致させる。既存の公開methodやtoolを不用意に増減しない。件数の過去値を現行値と決めつけない。
- 失敗した変更や取消後は、元入力・結果・ケース・比較表示を壊さない。非同期結果には入力版と世代を照合する。
- 大物物理タスクの材料点・幾何・転送の限定実装を、本番solver対応済みとして能力表へ掲載しない。
- 確認できる範囲だけを証拠に書く。Nodeの成功、ブラウザの成功、公開HTTPSの成功を分ける。

## 元PRを修正する9件の特別手順

27/28/29/30/34/37/38/39/40は、レビューで見つかった不具合の修正である。この9件では、通常のmain起点の作業場所作成に代わり、以下の元PR起点の手順を優先する。対象の元PRが未mergeなら、最新版mainに同コードがないことを理由に新規実装を始めない。

1. 個別指示のPR番号・head SHAを読み、`gh pr view <番号> --json headRefName,headRefOid,state`で最新状態を取得する。
2. `git fetch origin`で取得し、元PRが変わっていれば差分を再確認する。既に修正済みなら反例回帰を確認して報告する。
3. 元PR用worktreeに他人の編集中変更があれば触らない。自分の修正用branchとworktreeを、取得した元PR headから新規作成する。
4. 反例を先にテスト化し、失敗を確認してから修正する。反例の数値、ID、実測値を都合よく変更しない。
5. 修正・対象試験・証拠をcommitする。元PR headが進んでいないことを再確認する。
6. 許可済みの修正作業として、通常のfast-forward pushで元PR head branchへ反映する。例は `git push origin HEAD:codex/opencode-agentacp1`。対象名は各PRから取得する。force pushは禁止。拒否されたら他者変更を取り込む必要があるので停止して差分を報告する。
7. 同じ修正用の重複PRを作らない。元PRのCIとレビュー再確認を依頼する。自分ではmergeしない。
8. 元PRが既にmerge済みなら、最新mainを基点に修正PRを作り、元レビュー指摘との対応を記す。
