# エージェント運用を前提としたOSS CAEのターゲットと仕様

[English](en/product-direction.md)

策定日: 2026-10-14

Airpocket Simulation Studioは、利用者自身の計算資源を使い、インストール不要でCAEを始め、自分のLLMエージェントを通じて設計と解析を反復できるOSS CAE基盤を目指す。初心者が目的を伝えると、エージェントが必要情報を確認し、設定・解析・結果評価・設計へのフィードバックを進められる構成を重視する。

この文書は会話で示された製品方針と、それを実現するための仕様案をまとめる。目標機能は実装済みを意味しない。現在の実装範囲は[解析ガイド](analysis-guide.md)、公開進捗は`src/progress.json`を参照する。

## ターゲットと製品方針

- CAEの設定経験が少なく、自分のLLMエージェントに設定支援を任せたい設計者・開発者・学習者。
- ローカルCPU・GPUを活用して解析し、設計案を比較したい利用者。
- MCP・APIからCAEを組み込み、設計と解析の反復を自動化したい利用者。

製品の中心は、ブラウザでの利用開始、利用者の計算資源での実行、複数ソルバーの選択、エージェントが判断できるAPI、設計へのフィードバックである。GUIとエージェント操作の両方を提供し、利用者が設定と結果を確認できるようにする。

「インストール不要」はまずブラウザでのCAE利用を指す。エージェント接続まで追加インストールなしで実現することも目標とするが、接続方式は未決定。利用者のLLM環境に必要な設定とCAE側の要件を区別して公開する。ローカル計算であっても、外部LLMへ渡す情報は通信されるため、共有対象を説明する。

## 利用の流れ

1. 利用者がCAD形状と確認したい目的を伝える。
2. エージェントが形状・材料・条件を確認し、利用者にしか分からない情報を質問する。
3. エージェントが解析方法・ソルバー・メッシュ・境界条件を提案し、根拠と仮定を保存する。
4. APIが入力、単位、対応範囲、実行資源を検査する。
5. 必要なモジュールを取得し、利用者のCPU・GPUで計算する。
6. エージェントが収束、品質、適用限界を確認し、結果を説明する。
7. CADの変更案を作成し、再解析して変更前後を比較する。

## 共通APIとMCP

ブラウザ画面とMCPは共通の入力モデル・検査・実行・結果取得処理を利用する。LLMは設定案と解釈を担当し、機械的に判定できる整合性はプログラムで検査する。

以下はAPIの役割案であり、既存の関数名・MCPツール名ではない。

| 役割 | 取得・操作できる内容 |
|---|---|
| 対応能力 | ソルバーと版、物理分野、要素、材料則、境界条件、連成、CPU/GPU対応、必要入力、単位、有効範囲 |
| モデル確認 | 部品、単位、寸法、領域、材料、条件、設計版、現在の状態 |
| 入力作成 | STEP取り込み、領域指定、材料・条件・解析設定の登録 |
| 設定検査 | 不足入力、不整合、未対応設定、仮定、未確認事項、修正候補 |
| 実行準備 | 必要モジュール、取得量、キャッシュ状態、自由度、メッシュ品質、推定メモリ |
| ジョブ管理 | 実行、進捗、状態取得、中止、切断時の扱い |
| 結果評価 | 物理量と単位、収束、反力等の収支、品質指標、限界、ケース比較 |

複数ソルバーは共通設定と固有設定を分ける。「候補」「実装済み」「検証済み」を区別し、ソルバー変更で変換できない条件を返す。ライブラリ全体の機能を、そのアダプターの対応能力として扱わない。失敗時に黙って別ソルバーへ切り替えない。

### 構造化診断

診断には安定したコード、重要度、対象、検出根拠、修正候補、利用者の意図確認が必要かを含める。拘束不足、未対応材料モデル、メッシュ品質不足などを単なる文字列エラーで終わらせない。

修正可能性と物理的な妥当性は区別する。拘束不足に対して固定条件を自動追加するだけでは、実物の支持条件を表したことにならない。曖昧な支持・荷重は利用者に確認する。

### 根拠と仮定の保存

設定値には出所、資料と版・参照先、選定理由、仮定、確認状態、適用範囲を関連付ける。出所は利用者入力、材料資料、CAD、エージェント提案などを区別する。

未確認事項は解析前に検査する。必須入力が未定なら定量評価を止める。概算の仮定を明示して実行する場合は暫定解析として保存し、結果にも状態を引き継ぐ。LLMの確信度だけを物性や設定の根拠にしない。

## 初心者向けの解析手順

「荷重に耐えるか」「温度がどこまで上がるか」「共振を避けたい」など、目的別の手順を用意する。必要な質問、対応範囲、初期メッシュ、細分化判断、結果の評価方法を定義し、エージェントが利用する。

入力検査の成功、ソルバーの収束、物理的な精度を区別する。メッシュ依存性、特異点、材料仮定などを結果とともに説明し、初心者にも未確定部分が分かるようにする。

## ブラウザとエージェントの接続

現在のMCPは保存済みローカルJSONを操作し、開いているブラウザのセッションを変更しない。今後はブラウザの状態取得、設定変更、実行、中止、結果取得を共通セッションAPIへ接続する。

接続方式の検討案は、ローカル接続プログラムと、追加プログラムなしで接続するリレー方式。前者は初期検証に適し、後者はエージェント接続までのインストール不要という目標に対応する。どちらも計算場所と通信される情報を区別する。

セッションの接続許可、共有範囲、失効、切断、再接続、ブラウザ終了時の扱いを定義する。実行入力はスナップショットとして固定し、古い応答や途中の設定変更で結果を取り違えない。

## WASMの必要時取得と資源管理

基本画面は先に表示し、CAD読み込み、メッシュ生成、各ソルバー、高度な結果表示・出力を必要に応じて取得する。対応能力と入力仕様は小さな定義データとして取得でき、実行モジュールを取得する前にエージェントが選択できるようにする。

- 依存関係を解決し、未取得のモジュールだけをダウンロードする。
- 内容ハッシュと版でキャッシュ・整合性を管理し、使用版を結果へ記録する。
- 必要性が分かった段階で先読みする。材料や荷重の確認中にも準備を進める。
- ダウンロード、初期化、メッシュ生成、計算の進捗を分けて返す。
- 事前取得、保存容量確認、キャッシュ削除を提供する。ブラウザによるキャッシュ削除を扱う。
- ソルバーを専用Workerで実行し、反復中は再利用、不要時は終了してメモリを解放する。
- 独立してビルド・検証できる単位で分割し、共通ライブラリの重複も測定する。

配信する`.wasm`は開発側でビルド済みのバイナリである。ブラウザは端末向けにコンパイルし、インスタンスを初期化する。ブラウザによるコンパイル結果のキャッシュは保証せず、同一セッションのモジュール・Worker再利用を設計する。

待ち時間の確定値は未設定。代表形状で、圧縮済み転送量、初回取得、コンパイル・初期化、メッシュ生成、計算、再実行、ピークメモリを別々に測る。端末、ブラウザ、回線、キャッシュ状態を記録する。「基本画面は数秒以内」は目標案であり実測保証ではない。

## モジュール化とWASM版とネイティブ版

製品方針として、共通処理をモジュール化し、ブラウザ向けWASM版とローカル向けネイティブ版を提供する。ブラウザ版は導入不要の入口、ネイティブ版はローカルエージェントからの継続実行やブラウザ外の計算を担う。ネイティブ版には導入が必要であり、ブラウザ利用のインストール不要という要件と区別する。

| モジュール | 共通化する責務 | 環境固有の責務 |
|---|---|---|
| モデルと検査 | 入力、単位、根拠、診断、対応能力 | 永続保存の実装 |
| CADとメッシュ | 形状・領域の契約、品質指標 | 各ライブラリのWASM/ネイティブ呼び出し |
| ソルバーアダプター | 検査、入力変換、結果と収束の契約 | CPU/GPU、実行ファイル、並列処理 |
| 結果と比較 | 物理量、設計版、証跡、比較条件 | 画面描画、ファイル出力 |
| 実行管理 | ジョブ状態、中止、入力スナップショット | Worker、ネイティブプロセス、通信 |
| 操作窓口 | 共通APIの意味と診断 | Web UI、MCP、CLI |

全ソルバーを両環境に移植するとは限らない。対応能力に実行環境と制限を含め、WASM専用・ネイティブ専用も明示できる構成とする。同じ対応範囲の入力について、両版の単位、診断、結果スキーマを合わせ、数値結果は許容誤差と収支で比較する。完全なビット一致は前提としない。

既存Node経路はWASM実行であり、独立したネイティブ機械語版とは区別する。最初は共通検査と小規模線形構造で両版の契約を検証し、段階的に展開する。具体的な分割と移行時期は未決定。

## Rustの採用方針案

Rustは新規の入力検査、単位変換、診断、独自計算処理の候補とする。WASM版とネイティブ版で共通処理を利用できることを評価する。GUIは既存JavaScriptを活用し、Gmsh・OpenCASCADE・MFEMなどのC/C++資産を利用する。

全面移行は未決定。小さな共通検査モジュールで、連携、性能、サイズ、起動時間、保守性を検証して判断する。Rust採用だけでダウンロード量やブラウザのコンパイル処理が減るとは扱わない。

## SolidCraftとの設計反復

SolidCraftがパラメトリック設計・寸法変更を担当し、Airpocketが解析・評価を担当する。STEPを形状の主な交換形式とし、設計IDと版、ファイルハッシュ、パラメータ変更、部品と配置、名前付き領域、対応付けの根拠を連携情報として扱う案を検討する。

初期段階は既存の幾何照合と領域再選択を利用する。永続的な設計面参照の交換は別途検証し、面番号だけに依存しない。曖昧・消失・分割された領域を黙って別面へ割り当てない。変更後は条件を再検査し、メッシュを再生成する。

各結果に設計版、入力、ソルバー版、モジュール版、メッシュ、収束を保存する。設計変更と解析条件変更を区別し、比較の前提が異なる場合は表示する。STEP互換性と反復運用は実ファイルで検証する。

## OSSとしての公開と比較

比較の主軸は「初心者の意図から、エージェントが解析を成立させ、設計改善へ進められるか」とする。併せて導入要件、計算場所、対応ソルバー、構造化API、検証情報、再現性、CAD連携を評価する。

比較候補はFreeCAD FEM、PrePoMax、SALOMEとCode_Aster、Elmer、OpenFOAM、FEAScript、Stabileo。形状・メッシュ・GUI・ソルバー・ライブラリの役割が異なるため、機能数だけで順位付けしない。

公開に向けて、再現可能な例題、参照解と誤差、対応範囲、版固定の配布物、ビルド手順、ライセンス・依存通知、貢献案内を整える。テスト件数と解析精度を区別する。

## 実装順序案と受け入れ条件

1. 対応能力と構造化診断を共通API・MCPへ公開する。
2. 設定の根拠・仮定・未確認事項の保存と解析前検査を追加する。
3. STEPから解析入力を作成するAPIを整える。
4. モジュールの必要時取得と性能計測を整える。
5. ブラウザセッションとエージェントを接続する。
6. SolidCraftとの単一部品・線形構造の設計反復を成立させる。

最初の統合例題はブラケットとする。初心者が用途を伝え、エージェントが取り付け・荷重・材料・許容変位を確認し、設定根拠を保存して解析する。厚さを変えた3案を比較し、各案の設計版・条件・メッシュ・収束・結果を再現できることを確認する。

不正な単位、未対応材料、拘束不足、未解決CAD領域、取得失敗、切断、中止を扱い、失敗後も既存入力と結果を保持する。初回と再解析の時間・メモリを計測する。ブラウザCPU/GPUとMCPの実行経路を個別に検証する。

## 未決定事項

- API・診断・根拠情報の具体的スキーマと互換性方針。
- WASM分割単位、配布・キャッシュ方法、保持するWorker数。
- 計算規模、待ち時間、メモリの目標値と対象端末。
- Rustを採用する範囲と移行時期。
- SolidCraftとの面参照・連携情報の交換方式。
- 追加ソルバーの優先順位と各アダプターの検証範囲。
