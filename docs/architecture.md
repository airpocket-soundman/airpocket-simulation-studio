# 構成とプロジェクト分割

## 判断: 最初は一つのリポジトリ

構造・熱・流体は一つの製品にまとめ、内部モジュールと実行プロセスを分離する。3D表示、CAD上の部分領域、材料、ケース保存、ジョブ管理、結果表示を共通化でき、熱から構造への温度受け渡しや流体と固体の熱連成にもつながる。

流体専用の領域作成・境界層メッシュ・収束設定は構造画面に詰め込まず、解析種別ごとの画面で扱う。リポジトリを分けるのは、独立した配布・開発チーム・ライセンス上の必要が具体化したとき。ワーカーを別環境で動かすこと自体は別リポジトリを必要としない。

## 技術構成の案

音響も共通製品内の独立モジュールとする。固体の振動領域と空気等の音響領域を区別し、構造振動から音響境界へ受け渡す契約を設ける。流体騒音は通常の流体計算とは別のモデル・計算条件を必要とする。

- UI: TypeScript / React と Three.js 系の3D表示。実装前にCAD面との対応を試作検証。
- CAD・メッシュ: OpenCASCADE系のCAD処理とGmsh。可視化三角形から元のCAD面を追跡。
- ワーカー: Pythonを候補とし、ソルバーを外部プロセスで実行。Windows端末からWSL2/Linuxも利用できる境界を設ける。
- 結果: 変位・応力・温度・流速・圧力等を共通フィールドへ変換。VTK等の形式を候補に、節点／要素／積分点の差を保持。
- アダプター契約: capabilities、validate、export、run、cancel、collectResults。版、収束、診断情報も返す。

将来のディレクトリ案: apps/ui、packages/model、packages/viewer、workers、adapters/calculix、adapters/elmer、adapters/code-aster、adapters/openfoam、benchmarks。

## 保存モデル

Geometry → Region → Material / BoundaryCondition → Study → Mesh → SolverRun → Result。

RegionはCAD参照と表面上の領域定義を保持。SolverRunは入力のスナップショットを保持し、UI変更で過去の計算結果を上書きしない。物理量には単位を持たせ、内部の基準単位への変換を一元化する。

## 連成

まず別々の解析を成立させる。次に熱→構造の一方向連成、固体・流体の共役熱伝達へ進む。異なるメッシュ間の転送では温度補間、力・熱流の保存を検証。流体構造の双方向連成は後段とし、単に二つのソルバーを順番に動かしただけで対応済みにしない。
